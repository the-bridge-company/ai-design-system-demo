Patterns: one Library section, two kinds. A repository keeps one file per pattern in `patterns/<id>.pattern.json` (`{ id, kind, name, purpose }`). An interaction (`kind: "interaction"`) is keyed by a behavior id of the components' docs.json and exists only while two components or more list that id: which components do it, and each one's words and keys, are read from them, never written again (Close on Escape, Pick with Enter and Focus after a pick, on Select and Combobox). An action (`kind: "action"`) is a task people take across the product, with whether it can be undone, its rules, the DS components it uses, `usedIn` (the real places that do it, each with the file that holds its label and the text that file contains, checked by a test) and a stage. The shared rule: Undo in a Toast when it can be undone, an AlertDialog first when it cannot. Bridge ships Delete and Send for review (its button reads Send suggestion when a team sends suggestions), from an inventory of its own UI. Core validates and reads patterns (`validatePattern`, `readPatterns`, `patternGroups`), derives interactions (`behaviorUses`, `interactionsWithUses`, `interactionProblems`), gives the agent view (`agentPatterns`, `modelAgentPatterns`) and llms.txt lines (`patternLlmsLines`, also in a team's published llms.txt); the repo model reads them (`patterns`). The Library has a Patterns section: Overview, then each pattern by name under Interactions and Actions. An interaction page plays each component on the Behaviors stage; an action page plays the pattern with the real Button, AlertDialog and Toast, then its rules, components and where it is used. A component page's shared behavior rows link to their interaction. A team's Library shows Patterns only when its data has some. MCP: `bridge_list_patterns` and `bridge_get_pattern`.
